# 依赖部署与交叉编译

各目录和文档入口见[文档与代码清单](文档与代码清单.md)；Python 的独立构建和运行说明见 [Python 接入说明](../python_demo/doc/Python接入说明.md)。

## 1. 默认部署

首次使用时，在 SDK 根目录执行，无需指定或连接机器人：

```sh
bash deploy/deploy.sh
```

脚本检查构建工具和 GStreamer，构建或复用私有 DDS，再尝试在 `python_demo/.venv` 准备 Python/CFFI。确认后的工具链和参数保存到 `.deps/<工具链标识>/config.mk`，`.deps/active.mk` 记录当前选择，`deploy/deps.mk` 自动读取这些生成配置，客户无须修改 `config.mk` 或 `active.mk`。部署不构建 SDK 主程序、API 库或 Python 扩展，也不显示指令菜单。只需要 C/C++ 时加 `--skip-python`。默认不检查机器人网络、不修改机器人配置；旧入口 `deploy/deploy_ubuntu.sh` 转发到同一脚本。

部署完成后先显示“部署结果：”，再显示“后续操作指南：”。指南分为三项：编译、运行 SDK 前检查修改配置文件、SDK 运行方法。C/C++ 客户与 Python 客户按使用语言选择一项即可，无须两套都编译；命令采用 `cd ... && ...`，可以整行复制，切换目录失败时不会继续执行。配置板块只显示 `CodeProject/AheadFormSDK_Config.ini` 的完整路径。运行 SDK 前按目标机器人核对 `[dds] strNetworkInterface`（客户端网卡）、`domain_id`（外部 DDS 域），以及 `[media] strRobotIPv4`、媒体开关、组播和端口。切换机器人时只需修改配置并重启 SDK，无需重新部署或编译；项目自带 IP、域和网卡值不保证适用于现场。

“部署结果”列出 C/C++ 依赖环境是否准备成功，以及 Python/CFFI 环境是准备成功、失败还是按参数跳过。Python 准备失败时，在此板块显示具体原因；这不影响已经成功准备的 C/C++ 环境。交叉编译时 Python 状态只表示宿主机环境已准备，目标扩展仍需按目标 Python 配置构建。部署成功表示依赖环境准备完成，不代表 SDK 程序或 Python 扩展已经编译。

部署时在 `Selected toolchain and deploy:` 下集中显示编译器、当前 CycloneDDS/GStreamer Core/App 版本、`dds_cflags`、`dds_libs`、`gstreamer_cflags`、`gstreamer_libs`，以及已设置的 `PKG_CONFIG*`。默认输出不展示内部 `config.mk` 路径或 `.pc` 文件目录；末尾编译板块只显示客户可编辑的参数配置文件 `deploy/deps.mk` 和构建命令，并提示修改编译器或编译参数后，在所选语言的构建目录先 clean 再构建；Python 的 clean 会同时清理标准 API 库及其对象文件。普通源码修改仍直接 make，不重复依赖部署。这些信息来自当前选中的依赖环境：DDS 使用 SDK 私有的 CycloneDDS 静态库，客户系统已有的 FastDDS 或其他 DDS 不会被自动选中；客户自有 GStreamer 可通过 `PKG_CONFIG*` 指向兼容版本，详见[指定编译器](#4-指定编译器)和[交叉编译](#5-交叉编译)。

也可选填以下参数，省略的字段保留 INI 当前值：

- `--robot 实际IPv4`：检查机器人连通性，保存 IP；未传 `--interface` 时按通往该 IP 的路由选择有线网卡。不会自动推断或覆盖 DDS 域。
- `--domain 外部DDS域`：更新 DDS 域，范围为 `0～232`，可单独使用，无需提供机器人 IP。
- `--interface 网卡名`：更新客户端有线网卡，可单独使用；同时指定机器人 IP 时须与通往机器人的路由一致。

例如下面的 IP、DDS 域和网卡仅为示例，使用前替换为现场值：

```sh
bash deploy/deploy.sh --robot 192.168.110.51 --domain 50 --interface ens33
```

显式配置时仅修改对应字段；内容变化后先备份、再原子更新，保留注释、编码、换行和其他字段。只有指定 `--robot` 才需要用于连通性检查的 `ip`、`ping`；未传机器人参数时，不因缺少这两个工具而安装网络包。

**Python 是可选部署项。** CFFI 或 Python 开发环境准备失败时，脚本继续完成 C/C++ 依赖部署；只要核心依赖和所需机器人配置成功，退出码仍为 0。“部署结果”中分行打印 C/C++ 环境准备成功、Python 环境准备失败及具体原因。补齐依赖后重跑即可；部署不会改动现有 Python 扩展及其选择标记。主动 Ctrl+C/SIGTERM 仍取消部署；DDS、必需依赖及机器人配置错误仍使部署失败。后续手动构建扩展失败则由 make 正常报错，不影响已经准备好的 C/C++ 环境。

**同一套工具链和依赖环境只需成功部署一次。** 首次部署成功后需手动构建 SDK 程序；以后修改或新增 SDK 源码，按[普通 make](#3-私有目录与普通-make)构建，不必重复部署，也不用再次输入编译器。更换构建环境或依赖配置、DDS 缓存丢失/失效时才重新部署；只是修改机器人配置时，手动编辑 INI 并重启程序即可。

默认已可在没有机器人的情况下部署。若需要显式禁止自动配置（即使同时传入了机器人参数），保留以下兼容选项：

```sh
bash deploy/deploy.sh --build-only
```

已有依赖完整、需要断网构建时：

```sh
bash deploy/deploy.sh --build-only --skip-packages --jobs 4
```

要同时准备 Python 环境，私有 Python 环境和 requirements 也须已准备；首次离线安装 Python 包时加 `--python-wheelhouse /本地包目录`，缺项只影响 Python。`--skip-packages` 只禁止系统包管理器，不禁止 pip 联网。完全不尝试 Python 时加 `--skip-python`。

SDK 目录和源码路径不要包含空格。终端部署时先显示 C 编译器当前值，直接回车或等待 2 分钟保留当前值，输入新命令或完整路径后回车则修改。本机编译且无特殊要求时直接回车即可，需要指定时可填写 `gcc`、`clang` 或客户工具链的 C 编译器路径，具体示例见[指定编译器](#4-指定编译器)。默认读取 `deploy/deps.mk` 中明确填写的覆盖项和本次环境变量，再采用上次成功部署设置，首次使用系统 `cc`；文件覆盖项遵循 Make 的优先级，高于同名环境变量。配套 C++ 编译器、静态库工具和索引工具自动确定并展示，只有无法确定时才补问；不修改系统默认编译器。

每个实际提问独立等待 2 分钟；可选参数输入 `-` 清空，超时丢弃未提交输入。没有有效默认值时超时会退出。非交互终端不等待，也可显式跳过询问：

```sh
bash deploy/deploy.sh --build-only --skip-packages --non-interactive
```

不要用 `sudo` 运行整个构建；需要安装系统包时脚本单独提权。从 sudo 启动且有原用户身份时，会转回该用户构建。

## 2. 离线范围与系统依赖

SDK 随包提供完整、已解压的 CycloneDDS 11.0.1 源码，构建 DDS 不下载其他源码。所用精简配置关闭 IDLC、安全/TLS、iceoryx、测试、示例、性能工具和 LTO。构建依赖仍包括客户的工具链和目标 C 运行库。

客户需要准备：

- GNU/Linux 工具链及其开发文件；本工程保留 GNU/Linux 接口，不承诺 macOS 或其他操作系统可直接使用。
- Bash、Python ≥ 3.8、GNU Make、findutils、CMake ≥ 3.16、pkg-config、编译器配套的 ar/ranlib。
- 默认 Python 接入还需要匹配的 Python 开发头文件、venv/pip 和固定版本 CFFI；没有兼容 CFFI wheel 而需源码安装时，还需要构建主机的 libffi 开发文件。脚本支持补齐缺少的系统包，并仅在私有虚拟环境安装 Python 包。
- 目标平台的 GStreamer Core/App ≥ 1.20 开发包。
- 目标平台运行所需的 GStreamer 插件：App、UDP、RTP/RTP manager、H.264 parser、MP3 parser/mpg123 decoder、WAV parser、音频转换和重采样，以及 filesrc/decodebin/typefind。
- 正常部署检查网络时需要 ip、ping；仅构建时不需要。

开发包和插件通常来自 GStreamer base/good/bad 软件包组。脚本逐项检查实际插件，不只检查包名。APT、DNF、Zypper 家族仅在缺项或版本不足时安装或升级必要包；可能升级已有 GStreamer 1.x，但不安装系统 CycloneDDS、不添加软件源、不移除冲突包、不做整机升级。发行版仓库无法提供所需版本/插件时会报错，请使用受支持的新发行版或自行准备依赖。Arch 及其他发行版只检查并报告缺项。

`--skip-packages` 完全禁止系统包管理器操作；C/C++ 必需依赖缺项时报错退出，只有 Python 依赖缺项时继续 C/C++ 部署。它不禁止私有虚拟环境中的 pip 联网，离线安装 Python 包须另用 `--python-wheelhouse`。SDK 没有随包提供 GStreamer、编译工具或发行版软件包，因此“DDS 可离线构建”不等于“任意一台裸系统都能离线完成部署”。

## 3. 私有目录与普通 make

```text
ThirdParty/cyclonedds-11.0.1/   上游原始源码
ThirdParty/SHA256SUMS           源码校验清单
.deps/<工具链标识>/cmake/       DDS 构建中间文件
.deps/<工具链标识>/prefix/      私有头文件、libddsc.a 和 .pc
.deps/<工具链标识>/build.log    DDS 构建日志
.deps/<工具链标识>/config.mk    确认后的编译器、参数等 Make 默认值
.deps/active.mk                 当前 SDK 使用的本地配置
.deps/deploy-settings.json      上次成功部署的工具链设置
CodeProject/AheadFormSDK        真正的 ELF 可执行程序
python_demo/.venv/              项目私有 Python/CFFI 环境
python_demo/.build/             按工具链和 Python ABI 隔离的接入扩展
```

标识包含编译器身份、目标架构、sysroot、参数、源码清单和构建选项。成功的 DDS 产物在重复部署时复用，失败产物不能当作可用缓存。主动重建当前配置：

```sh
bash deploy/deploy.sh --build-only --skip-packages --rebuild-dds
```

DDS 的头文件参数通过限定到私有目录的 pkg-config 查询，最终链接明确选择私有 `libddsc.a`。不写入全局环境、不修改动态库搜索配置、不运行系统 ldconfig，不会让其他工程默认改用本项目的 CycloneDDS。GStreamer 查询继续使用客户的环境。

部署后，日常修改或新增 SDK 源码、头文件，只需从 SDK 根目录执行：

```sh
make -C CodeProject
```

也可在 `CodeProject` 中直接执行 `make`。构建会自动读取部署时保存的工具链和参数，只编译 SDK，既不重新解压 DDS，也不调用 DDS 的 CMake。普通修改无需先 clean；修改头文件会自动重编译受影响的源码，未变化的对象文件复用。

自动搜索范围是 **`CodeProject` 下除 `API` 以外的全部目录及子目录**，不局限于 `User`。例如在 `User`、`User/sub` 或新建的 `CodeProject/Customer` 下添加 `.c`、`.cpp` 和头文件，都无需修改 Makefile。C/C++ 源码可混合放置；API 仍只构建 `.c`，不要把 `.cpp` 放入 API。同一目录不得同时存在 `foo.c` 和 `foo.cpp`，整个程序只保留一个 `main()`；C++ 调用 C 接口的声明方式见[快速上手的移植方法](AheadFormSDK快速上手.md#5-移植方法)。

删除、重命名源码或将源码在 `.c`、`.cpp` 之间转换后，执行：

```sh
make -C CodeProject clean
make -C CodeProject
```

`clean` 同时清理主程序和 API 产物，保留 DDS 缓存；没有部署过依赖时也能 clean。相同工具链和参数下，切换主程序/API 构建入口无须清理。只修改 `AheadFormSDK_Config.ini` 无需编译，保存后从 `CodeProject` 目录重启 SDK。

更换编译器、目标架构、sysroot、编译/链接参数或 GStreamer 开发环境时，请用相应环境重新执行部署脚本，不要只在 make 命令中换参数。脚本只准备依赖并保存 `.mk` 参数，不清理或构建 SDK。已有旧产物时，C/C++ 客户执行 `make -C CodeProject clean`，Python 客户执行 `make -C python_demo clean`，再构建所需入口；有效 DDS 缓存会复用。依赖配置或 DDS 缓存丢失/失效时也需重新部署，缓存损坏时按报错加 `--rebuild-dds`。项目整体迁移到另一目录后，可直接 make；如果编译器、sysroot 或 GStreamer 本身也搬了位置，请按新路径重新部署。

不能更改客户系统包时，请先准备兼容环境并使用 `--skip-packages`。GStreamer 升级后仍需验证客户原有应用的插件行为。

## 4. 指定编译器

提示“选择 C 编译器（CC）”时，填写要生成目标 Linux 程序的 **C 编译器命令或可执行文件路径**：

| 使用场景 | 输入方法 |
| --- | --- |
| 在当前 Linux 上编译并运行，无特殊要求 | 直接回车，采用显示的当前值；首次默认为 `cc`。 |
| 指定已安装的 GCC | 输入 `gcc`，或实际的 GCC 可执行文件完整路径。 |
| 指定已安装的 Clang | 输入 `clang`，或实际的 Clang 可执行文件完整路径。 |
| 为另一台 Linux 设备交叉编译 | 输入客户工具链的 C 编译器，例如 `/opt/customer/toolchain/bin/aarch64-linux-gnu-gcc`；该路径仅为示例，还须按[交叉编译](#5-交叉编译)提供目标依赖环境。 |

`CC` 负责 `.c`，`CXX` 是同一工具链中负责 `.cpp` 的配套 C++ 编译器，通常由脚本自动确定；`AR`、`RANLIB` 是生成静态库及其索引的工具，不是另外两种编译器，通常也无需手动设置。若无法自动确定，按提示填写同一工具链的工具路径；也可在运行脚本前用环境变量明确指定。

例如使用已安装的 Clang：

```sh
CC=clang \
  bash deploy/deploy.sh --build-only --skip-packages
```

可通过标准环境变量传入 `CC`、`CXX`、`AR`、`RANLIB`、`CROSS_COMPILE`、`SYSROOT`、`CPPFLAGS`、`CFLAGS`、`CXXFLAGS`、`LDFLAGS`、`LDLIBS` 及 `PKG_CONFIG*`。这些参数记录到项目本地配置，统一用于 DDS 与 SDK；下次 make 无须再输入。常见 GCC/Clang 工具链通常只需指定 C 编译器。更换 C 编译器、sysroot 或编译参数后，会重新确定未明确指定的配套工具和目标依赖目录，避免混用旧设置。自定义厂商工具无法推导时，脚本会补问，也可通过环境变量显式提供；编译器需支持现有 Makefile 的 GCC/Clang 风格选项，例如 `-MMD`、`-MP` 和 `-pthread`。

API 以外的 `.c` 使用 `CC` 和 `CFLAGS`，`.cpp` 使用 `CXX` 和 `CXXFLAGS`，两者共用 `CPPFLAGS`；API 始终按 C 编译。存在 `.cpp` 时使用 `CXX` 链接所有对象及 API 库，否则仍使用 `CC`。Makefile 不强制 C++ 标准或优化级别。编译选项通过相应环境变量提供，不必填入 C 编译器的询问项。例如需要 C++17 时，在 SDK 根目录执行：

```sh
CXXFLAGS='-std=c++17' \
  bash deploy/deploy.sh --build-only --skip-packages
```

脚本成功后会保存这些设置，之后可直接 `make -C CodeProject`。如已有旧工具链或旧参数的产物，先 clean 再构建。`CPPFLAGS` 用于 C/C++ 共用的预处理参数（如 `-D`、`-I`），`CFLAGS`、`CXXFLAGS` 分别用于 C、C++ 编译参数，`LDFLAGS`、`LDLIBS` 用于链接参数和额外库。只有需要这些自定义设置时才提供。

### 通过 deps.mk 固定项目参数

也可编辑 [`deploy/deps.mk`](../deploy/deps.mk) 顶部的注释示例，取消需要项的注释并填写实际值，例如：

```makefile
CC := clang
CXXFLAGS ?= -std=c++17
```

只有 C 编译器有特殊要求时通常只填 `CC`，配套工具仍可自动推导。部署使用 GNU Make 读取这些设置，支持常规 Make 变量表达式。`?=` 只在变量未定义时提供默认值，适合 `SYSROOT`、编译参数和 `PKG_CONFIG*` 等可选设置，客户已提供的环境变量会优先。`CC`、`CXX`（以及 `AR`）已有 GNU Make 内建默认值，直接用 `?=` 无法覆盖，因此编译器示例保留 `:=`；不取消示例注释时仍采用部署保存的工具链。文件中使用 `:=` 固定的设置高于同名环境变量，想在终端改为其他值时，先更新或注释该固定项。

重新执行 `bash deploy/deploy.sh` 后，确认的输入会写入 `.deps/<工具链标识>/config.mk`（`DDS_DEFAULT_CC` 等字段），并更新 `.deps/active.mk`。这些是生成的本地配置，不随源码提交、不手改。原 Makefile 不会被脚本重写，后续手动 make 自动读取配置。改变工具链或编译/链接参数并重新部署后，已有产物须手动 clean 再构建。

## 5. 交叉编译

脚本根据编译器目标宏和工具链前缀识别目标，CMake 使用脚本传入的编译器及 sysroot，不会根据构建主机猜测客户板子的环境。可加 `--cross` 强制交叉模式。交叉模式仅准备依赖，不构建 SDK、不运行目标程序、不检测主机插件，也不将主机网卡写入配置；即使传入机器人参数也不在主机检查机器人或自动更新 INI，请在目标设备修改对应配置文件。

交互模式下会继续询问目标 `SYSROOT` 和 `PKG_CONFIG`。使用普通 pkg-config 时，再询问目标 `.pc` 目录及其 sysroot；使用客户包装脚本时，不重复询问其内部目录。每项显示当前值并等待 2 分钟，仍支持直接通过环境变量提供以下参数。

以下为仅准备 C/C++ 依赖的示例；如还需宿主 Python/CFFI 环境，请去掉 `--skip-python`，手动构建 Python 扩展时再提供第 8 节所述目标 `PYTHON_CONFIG`。路径均为示例，替换成客户已准备好的目标 sysroot 和 GStreamer：

```sh
CROSS_COMPILE=aarch64-linux-gnu- \
SYSROOT=/opt/customer/target-sysroot \
PKG_CONFIG_LIBDIR=/opt/customer/target-sysroot/usr/lib/aarch64-linux-gnu/pkgconfig:/opt/customer/target-sysroot/usr/share/pkgconfig \
PKG_CONFIG_SYSROOT_DIR=/opt/customer/target-sysroot \
  bash deploy/deploy.sh --cross --skip-packages --skip-python --jobs 4
```

ARM32 可改为相应的 `arm-linux-gnueabihf-` 工具链，并使用 ARM32 sysroot 和 GStreamer。也可用完整路径指定 CC/CXX/AR/RANLIB，或提供目标 pkg-config 包装器。DDS 的私有 .pc 由构建主机的 pkg-config 单独查询，目标包装器只用于 GStreamer，避免包装器内置的 sysroot 覆盖私有 DDS 路径。32/64 位、大小端、浮点 ABI、glibc 版本等必须与目标系统匹配；不能只更换一个编译器前缀。

交叉构建要求目标 GStreamer 的头文件、库及 .pc。包含 `.cpp` 时，还需配套的目标 C++ 编译器、标准库及运行库，不能混入主机版本。默认 pkg-config 未指定目标目录时会拒绝构建；随后还会做 DDS/GStreamer 链接探针，检查实际库是否可被目标编译器链接。目标板仍须安装匹配的 GStreamer 运行库和插件，交叉构建通过不能代替板上媒体运行验证。

## 6. 独立 API 静态库

先按相同工具链运行部署，再在 SDK 根目录执行：

```sh
cd CodeProject/API
make -f subMakefile_buildApiLib
make -s -f subMakefile_buildApiLib print-cflags
make -s -f subMakefile_buildApiLib print-libs
```

产物为当前目录的 `libAheadFormSDKApi.a`，只归档 API 对象。主 Makefile 也调用此入口构建 API 库，相同工具链和参数下切换入口无须清理；主入口的 `make clean` 会同时清理 API 产物，保留 DDS 缓存。第一条查询输出 API 和依赖的头文件/编译参数；第二条输出最终链接参数，其中包括 API 库、私有 DDS 静态库、GStreamer 和系统库。将链接参数放在调用方对象文件之后，使用相同的工具链与配套头文件。保留项目的私有 DDS 安装目录，不能只复制 API 的 .a 就省略 DDS 及 GStreamer。

默认最终程序不依赖 libddsc.so，但仍依赖目标系统的 glibc、GStreamer 及其插件，并非全静态程序。未部署、缓存缺失或参数不匹配时，请按报错重新部署。

需要 API 动态库时，从 SDK 根目录执行：

```sh
make -C CodeProject/API -f subMakefile_buildApiLib api_so
```

生成 `CodeProject/API/libAheadFormSDKApi.so`，不构建静态库和主程序。普通 `make` 仍只生成静态 API 库；静态库使用 `.o`，动态库按需使用 `.pic.o` 和 `-fPIC`，两类对象分别增量更新。动态库静态链接私有 DDS，运行时仍依赖匹配的 GStreamer 和系统库；`print-libs` 保留原静态链接用途。两种库都使用部署保存的目标工具链，交叉编译得到的动态库须由架构、ABI 匹配的目标进程加载。主入口 `clean` 同时清理两种 API 库和对象，保留 DDS 缓存。

## 7. 中断后重新部署

部署时按 Ctrl+C，或参数询问时遇到 EOF，会取消部署，不覆盖上次成功设置；重新运行同一命令后按当前提示继续。成功的 DDS 缓存经校验后复用，没有成功标记的构建重新配置并继续执行。部署不清理、构建或运行 SDK/Python 扩展，已有产物保持不变，普通 make 的增量行为不变。一次只允许一个部署进程操作同一 SDK 目录。

机器人配置内容未变化时，不重复写入或产生备份；发生变化时先备份再原子替换。工具链设置只在本次 C/C++ 部署及所需机器人配置成功后保存；可选 Python 失败不阻止保存。核心部署失败或主动中断不会将未完成的设置作为下次默认值。

系统包事务期间收到 Ctrl+C 或 SIGTERM，脚本会等待当前事务结束后再退出，请勿强制终止。强杀、断电等造成包数据库异常时，按系统包管理器提示恢复后重试；脚本不删除系统锁、不擅自扩大修复范围。

本次实际验证环境与边界见[部署验证记录](../deploy/VALIDATION.md)。

## 8. Python 接入构建

默认部署只准备 C/C++ 与 Python/CFFI 依赖。最终提示“Python/CFFI 依赖环境已准备”不代表扩展已构建；首次使用和日常修改后均须在 `python_demo` 手动 make，再运行示例：

```sh
cd python_demo
. .venv/bin/activate
make -j4 api                            # 仅 API；自动使用 .venv
make -j4                                # API + User
python demo_user.py --list               # 只列指令，不初始化机器人
python demo_user.py                      # 在 >> 下连续输入 User 指令
```

菜单示例需要包含 User 的默认构建；仅执行 `make ... api` 时只提供 API 接入。交互模式先初始化 SDK，成功后才显示输入说明和 `>>`；初始化失败报错退出，不接受指令。后续指令复用同一实例，`exit`、EOF 或 Ctrl+C 结束时释放。独立使用 `--help`、`--list` 或单次 `help`/`exit` 不初始化机器人。也可用 `python demo_user.py 指令 参数...` 单次执行；业务指令会访问机器人，运行前核对配置。

同一工具链和依赖成功准备后，日常修改源码或绑定声明只需重新 `make`，无需再次部署。Python 入口直接调用 API 子 Makefile 的 `api_so`，不重新构建 DDS，不改 SDK 总构建流程；CFFI 只生成 C，Make 使用部署保存的工具链编译。新增 API 只需补集中声明及必要类型，User 新增已注册命令无需 Python 分支。

标准 API `.so` 与 `.pic.o` 仍由 `CodeProject/API` 管理；CFFI 的两个扩展、生成代码、对象和元数据位于 `python_demo/.build/<DDS_BUILD_ID>-<Python ABI及配置标识>/`。`make -C python_demo clean` 删除 Python 的 `.build`，并调用 API 子 Makefile 清理标准 API 静态库、动态库及普通/PIC 对象文件；保留主程序及其 User 对象、DDS 缓存和 `.venv`。扩展通过相对运行路径使用同一份 API 动态库，API 内静态链接私有 DDS；不添加系统动态库搜索配置。

Python 3.8/3.9 使用 CFFI 1.17.1，Python 3.10 及以上使用 2.1.1，解释器须处于对应 CFFI 版本的支持范围；构建端与目标端使用一致版本。Python、CFFI、GStreamer 及工具链不属于 SDK 随包离线交付范围，可提前准备匹配平台的 wheel、传递依赖及开发包离线安装。

手动交叉构建 Python 扩展必须使用可在宿主执行的目标 `PYTHON_CONFIG` 包装脚本，提供 `--includes`、`--ldflags`、`--extension-suffix`；本机默认配置不适用于交叉目标。依赖部署阶段可先准备宿主 CFFI，无需目标 Python 配置；手动 make 缺少目标配置时会报错退出，不使用宿主头文件替代。使用 `make -C python_demo PYTHON=/宿主venv/bin/python PYTHON_CONFIG=/工具/目标-python-config api`。目标 Python 开发头文件（包括 `pyconfig.h`）、Python ABI、CFFI 后端、GStreamer 和系统库都须匹配目标；不能在宿主 Python 中加载目标扩展。完整包装脚本、离线步骤、运行限制及验证记录见 [Python 接入说明](../python_demo/doc/Python接入说明.md)。

交叉部署只准备宿主 Python/CFFI，不读取或构建目标 Python 扩展。目标 `PYTHON_CONFIG` 在每次手动 Python make 时传入。只需要 C/C++ 时加 `--skip-python`。目标板的 Python/CFFI 运行环境须另行准备，不能复制宿主 `.venv`。

提前下载匹配构建主机 Python 的完整 wheel 及传递依赖后，可断网执行：

```sh
bash deploy/deploy.sh --build-only --skip-packages --python-wheelhouse /本地/wheelhouse
```

本地包目录使用 pip `--no-index --find-links`，不访问包索引；请优先准备完整兼容 wheel，若使用源码包，还须准备其构建依赖。已有版本符合要求时不再调用 pip。普通 `make -C CodeProject` 仍只构建 C/C++；只需该语言时可用 `bash deploy/deploy.sh --build-only --skip-python`。
