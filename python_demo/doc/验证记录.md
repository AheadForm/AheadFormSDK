# CFFI 接入验证记录

验证日期：2026-11-27。环境为 Ubuntu 22.04.5 x86_64、CPython 3.10.12、CFFI 2.1.1；编译器覆盖 GCC 11 和 Clang 15.0.7。Clang 从发行版软件包提取至临时目录使用，未安装或替换系统编译器。最初 VM 缺少 ensurepip，绑定测试在临时 venv 中单独引导 pip，未修改系统 Python；后续默认部署已增加自动准备私有 Python 环境，验证见下文及[部署验证记录](../../deploy/VALIDATION.md)。

所有编译、探针、源码增删和迁移测试均在 `/tmp` 的 SDK 副本中进行，不向原工程写入构建产物。真实 SDK 仅加载、枚举 17 条指令、执行 `help`/`exit`；未调用真实 `AheadForm_Init()`，未执行机器人业务指令。

## 默认部署准备 Python

新增默认部署逻辑在 Ubuntu 隔离容器验证：自动补齐 venv/pip 和开发文件、在项目 `.venv` 安装 CFFI，并同时构建 C/C++ 主程序及 Python API/User 扩展。随后断网重新创建虚拟环境，使用 `--python-wheelhouse` 安装并构建通过；重复部署复用已有包，直接 `make` 自动选择私有 Python。`--skip-python` 在没有私有环境时仍能完成纯 C/C++ 部署。

本次 `.venv` 约 21 MiB，不含系统 Python/开发包；系统 Python 未安装 CFFI。15 项 Python 替身测试和 40 项部署回归通过，包括部署后直接 make 的参数空白一致性检查。新 Python 部署的实际包安装只验证 APT，未新增完整 ARM Python 交叉构建验证，详见[部署验证记录](../../deploy/VALIDATION.md)。

随后增加 Python 可选失败处理：在虚拟机临时副本用空离线包目录实际复现 CFFI 安装失败，再用临时 `#error` 实际复现扩展编译失败，两者均保留成功的 C/C++ 部署、退出码为 0，脚本最后再次显示 Python 未就绪及失败原因。清除失败的 Python 选择标记并保留缓存，恢复源码后重跑成功，加载并枚举 17 条 User 命令。新增降级、最终输出和中断边界验证后，部署回归共 46 项、原有 Python 替身测试 15 项通过；未操作机器人或修改虚拟机系统包。

## 替身测试

`python -m unittest discover -s tests -v` 共 15 项（原有 9 项加 6 项交互/命令行测试），GCC 和 Clang 均通过。测试编译 CFFI 自动生成绑定，链接临时假 SDK/User 实现，不执行真实机器人初始化：

- 常用结果、64 位时间和目标 ID、模块指针、通用绑定、重复关闭、非有限浮点输入。
- 原有符号错误码、超时、回复拒绝、暂无缓存、读取失败及输出缓冲区不被擅自改写。
- 初始化失败不调用释放且禁止重试；释放失败不再次释放。
- 单活动实例、多线程调用串行，以及成功关闭后另一实例可打开。
- User 命令表、大小写匹配、含空格参数、独立可写参数、未知命令、参数上限及 NUL 检查。
- 客户删除 Python 引用后，模块仍保持活动控制对象；初始化/释放失败时也保留控制对象，阻止新实例重试。
- 原 User `exit()` 错误路径仅在独立子进程结束，不影响测试进程。
